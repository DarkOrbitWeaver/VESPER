## 2026-11-17 continuation: atomic queue movement, safe cancellation and two-phase restart

This is the **larger follow-up batch** after transfer/checkpoint progress commit `9174549`, on isolated `codex/vesper-continued`. It adds **14 Windows .NET regression cases** to the 963-test baseline. This is narrow engineering evidence, **not** release approval or actual installed Chrome validation.

- **Queue positions:** `MoveInQueue` previously changed live order before saving, and Up/Down saved the neighbor and selected rows in two separate transactions. Four new `QueueMoveAtomicityTests` failed against the original behavior (one-sided SQLite commits and misleading Top/Bottom memory state) then passed. `JobStore.SaveQueueOrders` now atomically updates only `queue_order` for one/two existing rows, avoiding stale full-row writes to progress. Position changes become live only after SQLite's transaction commits. Both adjacent items now send their UI change events; queue-order extreme bounds refuse overflow. **Still open:** long-lived integer normalization and real UI ordering/performance tests.
- **HLS stop and Cancel:** `StopAndKeepLive` now persists the stop-request cursor **before** setting active `StopIntent`, cancelling the runner, or displaying success; idle stop similarly persists before requeue. The new loopback active recording test injects a refused SQLite stop save, proves the original capture remains live and unrevised, then removes the fault and confirms a **byte-exact, stopped playable file**. The idle live-stop error and idle Cancel error similarly leave their previous state untouched. Cancel still explicitly removes owned unfinished files, not completed files or Chrome-owned bytes.
- **SQLite deletion:** `JobStore.Delete` now removes a job and its associated browser submission claim in **one transaction**. Two tests inject failures at either table and confirm neither row becomes orphaned; the retry removes both cleanly. No changes to the browser's existing ownership policy.
- **Restart from scratch:** Before this batch it deleted saved bytes/sidecars before changing the durable job row. A failed SQLite update could therefore leave a Queued/old-progress record pointing to deleted bytes. Now the explicit confirmed restart persists `NeedsAttention/restart-cleanup` first; it validates/removes only exact owned .vpart/.vmeta/media files; then (and only then) saves a zero-progress Queued row, resetting validators and verification state. A rejected initial write leaves bytes untouched. A rejected final write leaves the safe non-running marker recoverable after restart, and unsafe paths cannot delete unrelated files. Four new `RestartAtomicityTests` exercise these boundaries. This does **not** constitute real process-kill or power-loss proof.
- **Cleanup preflight:** `TryRemoveCancelledFiles` now checks all known owned temporary paths before deleting the first one, then rechecks while deleting. The new test proved that the prior code deleted the main partial before detecting a later `.vmeta` directory; it failed before the fix and now passes. A live filesystem race between verification and deletion is still possible and belongs to Q1/Q8.
- **Critical post-crash restart guard (red→green):** An initial persisted `restart-cleanup` marker correctly prevented automatic scheduling, but the ordinary `Resume`/ `Start now` command could previously remove that marker and enter `Resolving` on a missing partial. A test reproduced this after `Harness.Restart`, then verified the fix. `Requeue` now rejects the pending cleanup state; `StopAndKeepLive` and HTTP `ReplaceLinkAsync` (including race-checked `ApplyRescue`) also reject this backdoor. The fourth `RestartAtomicityTests` case verifies a parked HLS recording cannot be requeued using live-stop. The intended recovery paths are explicit Restart from scratch or Cancel; browser/source refresh and true crash interruption still need their own review.
- **Verification:** **977/977 Windows .NET Release tests** pass (engine 559, resolver 357, Windows UI 41, setup 20), zero failures/skips; **126/126 Node Chrome extension mock tests** pass. Test counts alone do not imply release readiness.
- **Still open:** active cancellation/finalization stress, actual power interruption and WAL failure recovery, `MediaSourceRefresh`, browser authorization and native handoff, direct state saves and `OnRunFinished`, real DPI/Narrator/installer/media compatibility, measurable long-session performance, full audit reconciliation and Q0–Q10.

## 2026-11-17 continuation: transfer mutations and checkpoint progress must commit once

This checkpoint follows the verified UI-command atomicity commit `4d49553` on the isolated `codex/vesper-continued` branch; it is a bounded correction, **not** certification of every storage or media operation.

- **Transfer metadata durability:** `DownloadEngine.UpdateJob` formerly called `mutate(job)` before the SQLite write. Rejected updates could leave the live source URL, duplicate lookup, reason, timestamps, and committed extents at odds with the database. It now builds a detached `CopyForUpdate` candidate, invokes the mutation **once**, saves it to SQLite, then copies all mutable properties onto the original live `DownloadJob` under the engine lock. `ApplyPersistedState` is intentionally explicit, and a reflection-based regression compares **every public mutable property** so adding new properties cannot silently omit them. Active runner references remain the same; the mutation isn't replayed after the commit.
- **Real checkpoint overwrite bug (red → green):** `CommitCheckpoint` wrote flushed bytes/extent generation to SQLite but returned before its caller updated the live job. A simultaneous ordinary metadata update could then overwrite committed extents with stale zero progress. A deterministic test wrote and flushed **8,192 bytes**, committed them, then performed the metadata save; SQLite recorded **zero** before the fix. `CommitCheckpoint` now advances in-memory `Extents`, `Generation` and `MediaState` immediately after SQLite succeeds, **inside the same engine lock**. No pending bytes are declared committed before the disk flush or database commit.
- **Evidence:** four `TransferMutationAtomicityTests` pass, including failed-write preservation of source/index/byte-exact partial, single-execution timestamp parity, all-property copy, and the checkpoint interleave. Windows Release solution **963/963** tests (engine **545**, resolver **357**, WinForms **41**, installer **20**) pass with no skips or failures; the Chrome extension Node mock suite independently passed **126/126**, not a real-browser session.
- **Still OPEN:** the rest of `USER-ATOMIC-STATE`—multi-row queue moves, StopAndKeepLive, Cancel/RestartFromScratch and cleanup, browser handoff, media refresh, direct `SaveLocked` call sites, completion, real concurrent sessions and long-lived crash/power-loss tests. Also check the cost of deep-cloning extent metadata under heavy segmented workloads. Q0–Q10 stay OPEN.

## 2026-11-17 continuation: ordinary UI actions no longer publish failed SQLite updates

- **Red-green defect proof:** isolated SQLite `BEFORE UPDATE` fault-injection tests originally proved that Pause, Resume, Priority, Speed Limit and Rename changed the visible job although the write failed. All five failed before the fix and now pass; approval of unverified resume and a failed forced StartNow round out **seven** targeted cases.
- **Fix:** `DownloadEngine.Commands.PersistUiMutationLocked` stages only deterministic scalar edits on `DownloadJob.CopyForUiMutation()`, persists that candidate, and then applies the same edit to the original live object under `_lock`. Existing session references and checkpoint extents are preserved. Pause, Requeue/StartNow, limiter updates and `UpdateIfExists/UpdateIfIdle` publish their live state and side effects only after SQLite accepts the edit; the idle gate is checked in the same lock.
- **Verification boundary:** seven focused `JobCommandAtomicityTests` passed on the Windows RAMCA host. The original `952/952` .NET and `126/126` extension checks were previous-commit baselines, not this continuation's complete approval. `USER-ATOMIC-STATE` is still PARTIAL; `UpdateJob`, multi-row queue moves, Cancel, StopAndKeepLive, restart-from-scratch, browser/media refresh and runner completion still require independent atomicity and restart/failpoint proofs. Q1/Q9 and every release gate remain OPEN.

Instagram now has a bounded page-embedded video fallback; current provider gaps include live Instagram authorization/story verification and live verification of YouTube Mix paging.

VESPER only uses page data or explicitly authorized browser observations, reports sign-in walls, and does not call Meta APIs or replay private GraphQL requests.

## Additional reliability work

- Unknown-length bodies now get a one-byte range probe when the source advertises ranges. A source that reports remaining bytes after a clean early close stays unpublished. Close-delimited bodies with no framing or range proof stay in the partial file with a useful NeedsAttention reason; well-framed chunked and HTTP/2 responses remain usable.
- HTML error pages are detected from response headers and the first body bytes, including `text/html` attachments and mislabelled archive downloads. The partial file is kept and an HTML response is never published as the requested media file.
- TikTok now parses universal, SIGI and `__NEXT_DATA__` player layouts and reports private/login and region statuses with typed errors. The existing signed-address parsing and mirror handling remain.
- Refreshed HTTP and live-HLS sources carry validated Cookie/Authorization headers only to the replacement origin. Credentialed merge refresh supports direct tracks on one exact origin: it range-probes every candidate track, then commits the replacement plan and in-memory credentials together. A failed probe preserves the old URLs, bytes and credentials. Saved clip/output ranges are retained when the refreshed tracks have identical byte identity. Secrets are never serialized and are lost on restart, which requires a fresh authorized resolution. Cross-origin and segmented credentialed merge plans remain unsupported; 401/403/407 responses explain the likely recovery step.
- Automatic Chrome handoff retries temporary native-host errors without changing the Chrome download owner or transfer identity. Unexpected capture exceptions now create a bounded, URL-free popup explanation and a manual Transfers action when capture is enabled. The error wrapper does not initiate a pause or cancellation; the handoff path still requires native readiness and arms its recovery record before parking Chrome. Unconfirmed signed URLs are kept in bounded session storage. SameSite fallback now withholds cookies unless host and scheme match exactly.
- Right-clicking an ordinary page or button first asks that frame's VESPER player to open the existing format picker; if the frame has no player, it opens native page discovery instead. The menu is registered for page and frame contexts, uses the clicked frame for scoped auth, and never replays the control's click or POST.
- Smart Select now proposes an inline page SHA-256 only when one clearly labelled hash is adjacent to a scope containing exactly one reusable file link. The bridge forces checksum-bearing requests through native review. The review shows the full hash and page origin; a default-off checkbox is required before it reaches the engine. The engine verifies it before publication and retains mismatches as Suspect. No checksum sidecar is fetched, and ambiguous or unlabelled hashes are ignored.
- Chrome interception boundary: Chrome MV3 cannot cancel arbitrary download requests for a normal unpacked extension. VESPER accepts only a newly observed, still-unstarted Chrome download for which Chrome reports zero received bytes; a completed or already-progressing Chrome download remains Chrome-owned. Even for eligible requests the helper checks response identity before Chrome is paused, and the native transfer must be accepted before VESPER lists it. Context-menu "Download with VESPER" bypasses Chrome's normal download start for explicitly chosen links. Live Chrome/native-host behavior remains unverified; see USER-OWNERSHIP in the register.
- Chrome completion recovery: a previously missing release routine is now implemented. When Chrome completes its own file during a staged/accepted VESPER capture, the worker first records a durable native-cleanup state and requests abandonment; it never deletes Chrome's completed item. Offline or slow native cleanup stays recoverable through a one-minute alarm, including after MV3 worker restart. Three new extension tests cover normal release, unavailable native host, and Chrome-only completion. Browser integration remains to be verified with a real native host.
- Chrome recovery now pins each tentative transfer to a SHA-256 digest of the exact initial HTTP(S) source URL, rather than storing signed addresses or credentials. After native readiness, pause, acceptance, and worker-restart reconciliation, a changed source fails closed and the Chrome copy is kept/resumed. Legacy records with no digest also fail closed. Even after native completion, Chrome cancel/erase is allowed only for a still-paused zero-byte matching download, with a second state check and confirmation of Chrome cancellation. Four additional extension tests cover changed redirects, recovery after source changes, legacy records, and failed cancellation; the browser-level check is still pending.
- Optional “Prepare video formats in advance” is off by default. It makes metadata-only requests for visible non-DRM players, keeps results in a bounded 30-second memory cache, cools down repeated work per tab and clears results when the page changes.
- The Rescue window now offers manual refresh for an active live-HLS recording and checks the next playlist sequence before resuming it. The prefetch preference lives in the extension because the browser owns the page/player and the work; there is no duplicate desktop toggle without a supported settings-sync channel.
- Instagram blob players can now present direct or manifest URLs observed on the active frame/document within 15 seconds before or after player metadata. When multiple sources match, the picker requires a user choice and shows type/size hints without exposing signed query strings. It excludes partial 206 ranges unless headers show the full object. The response body is still fetched and verified by VESPER. Observed signed URLs are pruned from session storage after 10 minutes; the cache is capped at 25 sources per tab and 200 total across tabs. A response still cannot be tied to one exact video element when several players share a frame, so a coincident ad within the window remains ambiguous. This remains a public/browser-observed path; it does not add an unofficial API or a story/authentication bypass. [Meta's Instagram oEmbed API returns embed HTML](https://developers.facebook.com/docs/graph-api/reference/instagram-oembed/); the [Instagram Media API requires a user access token and may omit `media_url` for copyright-restricted content](https://developers.facebook.com/docs/instagram-platform/reference/instagram-media/v21.0/).
- Instagram page discovery now reads bounded `data-sjs` video-version URLs already embedded in accessible post, Reel, TV and story HTML. Carousel video slides become separate resolved album items; ordinary item discovery checks only the first playable slide and offers the rest through Browse. It probes through the shared pipeline, caps carousel discovery at 20 slides and the page candidate budget, and excludes image slides. Sign-in redirects produce LoginRequired; metadata without a playable URL points to browser discovery. It does not call GraphQL or an account API. A live attempt at the public upstream Reel fixture `Chunk8-jurw` failed on the first page request with `HttpRequestException` (84 ms; one request), before parsing or transfer, so it does not validate or disprove the adapter. No signed-in, private, story-sequence or Chrome fixture was available. [Current upstream yt-dlp uses page JSON and GraphQL strategies](https://raw.githubusercontent.com/yt-dlp/yt-dlp/master/yt_dlp/extractor/instagram.py); Meta's [official Media API](https://developers.facebook.com/docs/instagram-platform/reference/instagram-media/v21.0/) is access-token scoped and can omit media URLs.
- The in-page picker now constrains flex children, clamps long titles and hides horizontal overflow; format labels and output controls can wrap within narrow viewports. Static CSS regression coverage passes; visual Chrome/DPI/accessibility review is still pending.
- Destination paths now expand environment variables and normalize once at the path-safety boundary. Settings loads and saves the normalized default; Add Download, quick download and batch review submit the resolved path, while engine options use the same normalized value. File details show the resolved absolute path instead of a literal `%USERPROFILE%` token. Regression tests cover expansion, display, parent-segment rejection and settings reload.
- Downloads settings now offer an optional filename template using `{name}` and `{host}`. The extension remains at the end, the live example is sanitized, and invalid or unsupported placeholders block Save. The engine applies it to initial names and server-provided filenames; an empty setting preserves existing names. Focused engine and settings tests pass. Review the scrolled settings layout at Windows DPI scaling before release.
- The main-window footer now forecasts remaining storage by destination volume. It sums only known direct HTTP/original-container sizes, subtracts durable bytes already saved, and adds the engine's per-volume reserve. Conversions, segmented/live media, unknown sizes and unresolvable destinations remain explicitly unknown. Free-space probes run off the UI thread, are capped at 16 volumes and refresh at most once a minute while unfinished jobs exist; the accessible tooltip lists per-volume estimates and unknown counts. The warning is informational and does not alter transfer behavior; current free space can change while other applications write.
- Browser settings now offer a user-triggered local diagnostics ZIP with only system/build metadata, the scrubbed event log and a contents note. It excludes settings, databases, downloads and stored credentials; event filenames remain visible and the UI asks users to review before sharing. Scrubbing handles URLs embedded anywhere in a log line, URL credentials and queries, authorization/cookie headers including JSON-shaped headers, token-like assignments and the current profile path. The archive is written beside the destination and replaces an existing file only after it is complete; a failed replacement preserves the previous archive. Engine archive/redaction tests and Windows settings accessibility tests pass.
- Compatible AAC-only MP4→M4A and H.264/AAC MP4→MP4 outputs use lossless local remuxing instead of Media Foundation. Independent remuxes have their own two-job limit and no longer wait for the exclusive encoder slot: only actual transcoding (including the AAC conversion inside mixed-track remux) holds that gate. Two fixture outputs completed while the encoder slot was reserved, and an injected encoder correctly waited; output codec/sample integrity tests passed. Direct remux stages now use one final durable flush after any metadata edits, rather than flushing to disk twice. The earlier single-file timing is not evidence of a new throughput improvement. WAV and unsupported codecs still require the converter.
- Main-window engine events are coalesced before posting to WinForms. If an update arrives before the window's first native handle exists, the pending snapshot is now drained on handle creation instead of remaining stuck until another update. An STA lifecycle test verifies this, and both main-window test classes run sequentially to avoid concurrent access to shared GDI+ menu assets.
- Native unfinished-download **Cancel** is now one action: stop the job, wait for its runner to relinquish all file handles, delete its exact owned `.vpart`, recovery and media staging files, then remove the durable entry. No saved progress or second discard action is offered. Multi-select uses Cancel for unfinished-only selections and Remove for completed-only selections; mixed selections cannot silently combine deletion and history removal. A failed or unsafe cleanup keeps the entry visible for retry instead of claiming cancellation succeeded. Completed/publishing files, Chrome-owned files, link/placeholder paths and unrelated downloads are protected; the existing temporary-file layout is unchanged. Focused active-transfer, other-job isolation, path-tampering, cleanup-failure and WinForms menu tests cover this behavior; an end-to-end installed-app visual run remains open.

## Compatibility and operational limits

No runtime dependency, language, alternate UI framework or database migration was added to VESPER. Native SQLite and durability/publication contracts remain. Enum output values were appended, not renumbered. New bridge fields are optional; an old extension will not gain the new controls. Use the matching 1.0.2 app/extension for integration.

Secrets are absent from plans, recovery manifests, test fixtures, delivery reports and archives. A private transfer that loses its in-memory context on restart must re-authorize/re-resolve rather than replay credentials to another host. Authenticated merge/DASH contexts unsupported by the existing engine are still rejected rather than silently discarded. Do not use the live example's expiring URL as a fixture.

The workspace preview is only a read-only file explorer over real source and deliverables. It is not part of VESPER, not in its patch, and introduces no Next.js/PostgreSQL dependency into the Windows application.
