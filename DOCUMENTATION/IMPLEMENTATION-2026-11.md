## 2026-11-17 continuation: atomic queue movement, safe cancellation and two-phase restart

This is the **larger follow-up batch** after transfer/checkpoint progress commit `9174549`. It adds **14 Windows .NET regression cases** to the 963-test baseline. This is narrow engineering evidence, **not** release approval or actual installed Chrome validation.

- **Queue positions:** `MoveInQueue` previously changed live order before saving, and Up/Down saved the neighbor and selected rows in two separate transactions. Four new `QueueMoveAtomicityTests` failed against the original behavior (one-sided SQLite commits and misleading Top/Bottom memory state) then passed. `JobStore.SaveQueueOrders` now atomically updates only `queue_order` for one/two existing rows, avoiding stale full-row writes to progress. Position changes become live only after SQLite's transaction commits. Both adjacent items now send their UI change events; queue-order extreme bounds refuse overflow. **Still open:** long-lived integer normalization and real UI ordering/performance tests.
- **HLS stop and Cancel:** `StopAndKeepLive` now persists the stop-request cursor **before** setting active `StopIntent`, cancelling the runner, or displaying success; idle stop similarly persists before requeue. The new loopback active recording test injects a refused SQLite stop save, proves the original capture remains live and unrevised, then removes the fault and confirms a **byte-exact, stopped playable file**. The idle live-stop error and idle Cancel error similarly leave their previous state untouched. Cancel still explicitly removes owned unfinished files, not completed files or Chrome-owned bytes.
- **SQLite deletion:** `JobStore.Delete` now removes a job and its associated browser submission claim in **one transaction**. Two tests inject failures at either table and confirm neither row becomes orphaned; the retry removes both cleanly. No changes to the browser's existing ownership policy.
- **Restart from scratch:** Before this batch it deleted saved bytes/sidecars before changing the durable job row. A failed SQLite update could therefore leave a Queued/old-progress record pointing to deleted bytes. Now the explicit confirmed restart persists `NeedsAttention/restart-cleanup` first; it validates/removes only exact owned .vpart/.vmeta/media files; then (and only then) saves a zero-progress Queued row, resetting validators and verification state. A rejected initial write leaves bytes untouched. A rejected final write leaves the safe non-running marker recoverable after restart, and unsafe paths cannot delete unrelated files. Four new `RestartAtomicityTests` exercise these boundaries. This does **not** constitute real process-kill or power-loss proof.
- **Cleanup preflight:** `TryRemoveCancelledFiles` now checks all known owned temporary paths before deleting the first one, then rechecks while deleting. The new test proved that the prior code deleted the main partial before detecting a later `.vmeta` directory; it failed before the fix and now passes. A live filesystem race between verification and deletion is still possible and belongs to Q1/Q8.
- **Critical post-crash restart guard (red→green):** An initial persisted `restart-cleanup` marker correctly prevented automatic scheduling, but the ordinary `Resume`/ `Start now` command could previously remove that marker and enter `Resolving` on a missing partial. A test reproduced this after `Harness.Restart`, then verified the fix. `Requeue` now rejects the pending cleanup state; `StopAndKeepLive` and HTTP `ReplaceLinkAsync` (including race-checked `ApplyRescue`) also reject this backdoor. The fourth `RestartAtomicityTests` case verifies a parked HLS recording cannot be requeued using live-stop. The intended recovery paths are explicit Restart from scratch or Cancel; browser/source refresh and true crash interruption still need their own review.
- **Verification:** **977/977 Windows .NET Release tests** pass (engine 559, resolver 357, Windows UI 41, setup 20), zero failures/skips; **126/126 Node Chrome extension mock tests** pass. Test counts alone do not imply release readiness.
- **Still open:** active cancellation/finalization stress, actual power interruption and WAL failure recovery, `MediaSourceRefresh`, browser authorization and native handoff, direct state saves and `OnRunFinished`, real DPI/Narrator/installer/media compatibility, measurable long-session performance, full audit reconciliation and Q0–Q10.

## 2026-11-17 continuation: transfer mutations and checkpoint progress must commit once

This checkpoint follows the verified UI-command atomicity commit `4d49553`; it is a bounded correction, **not** certification of every storage or media operation.

- **Transfer metadata durability:** `DownloadEngine.UpdateJob` formerly called `mutate(job)` before the SQLite write. Rejected updates could leave the live source URL, duplicate lookup, reason, timestamps, and committed extents at odds with the database. It now builds a detached `CopyForUpdate` candidate, invokes the mutation **once**, saves it to SQLite, then copies all mutable properties onto the original live `DownloadJob` under the engine lock. `ApplyPersistedState` is intentionally explicit, and a reflection-based regression compares **every public mutable property** so adding new properties cannot silently omit them. Active runner references remain the same; the mutation isn't replayed after the commit.
- **Real checkpoint overwrite bug (red → green):** `CommitCheckpoint` wrote flushed bytes/extent generation to SQLite but returned before its caller updated the live job. A simultaneous ordinary metadata update could then overwrite committed extents with stale zero progress. A deterministic test wrote and flushed **8,192 bytes**, committed them, then performed the metadata save; SQLite recorded **zero** before the fix. `CommitCheckpoint` now advances in-memory `Extents`, `Generation` and `MediaState` immediately after SQLite succeeds, **inside the same engine lock**. No pending bytes are declared committed before the disk flush or database commit.
- **Evidence:** four `TransferMutationAtomicityTests` pass, including failed-write preservation of source/index/byte-exact partial, single-execution timestamp parity, all-property copy, and the checkpoint interleave. Windows Release solution **963/963** tests (engine **545**, resolver **357**, WinForms **41**, installer **20**) pass with no skips or failures; the Chrome extension Node mock suite independently passed **126/126**, not a real-browser session.
- **Still OPEN:** the rest of `USER-ATOMIC-STATE`—multi-row queue moves, StopAndKeepLive, Cancel/RestartFromScratch and cleanup, browser handoff, media refresh, direct `SaveLocked` call sites, completion, real concurrent sessions and long-lived crash/power-loss tests. Also check the cost of deep-cloning extent metadata under heavy segmented workloads. Q0–Q10 stay OPEN.

## Additional reliability work

- Unknown-length bodies now get a one-byte range probe when the source advertises ranges. A source that reports remaining bytes after a clean early close stays unpublished. Close-delimited bodies with no framing or range proof stay in the partial file with a useful NeedsAttention reason; well-framed chunked and HTTP/2 responses remain usable.
- HTML error pages are detected from response headers and the first body bytes, including `text/html` attachments and mislabelled archive downloads. The partial file is kept and an HTML response is never published as the requested media file.
- TikTok now parses universal, SIGI and `__NEXT_DATA__` player layouts and reports private/login and region statuses with typed errors. The existing signed-address parsing and mirror handling remain.
- Refreshed HTTP and live-HLS sources carry validated Cookie/Authorization headers only to the replacement origin. Credentialed merge refresh supports direct tracks on one exact origin: it range-probes every candidate track, then commits the replacement plan and in-memory credentials together. A failed probe preserves the old URLs, bytes and credentials. Saved clip/output ranges are retained when the refreshed tracks have identical byte identity. Secrets are never serialized and are lost on restart, which requires a fresh authorized resolution. Cross-origin and segmented credentialed merge plans remain unsupported; 401/403/407 responses explain the likely recovery step.
- Automatic Chrome handoff retries temporary native-host errors without changing the Chrome download owner or transfer identity. Unexpected capture exceptions now create a bounded, URL-free popup explanation and a manual Transfers action when capture is enabled. The error wrapper does not initiate a pause or cancellation; the handoff path still requires native readiness and arms its recovery record before parking Chrome. Unconfirmed signed URLs are kept in bounded session storage. SameSite fallback now withholds cookies unless host and scheme match exactly.
- Right-clicking an ordinary page or button first asks that frame's VESPER player to open the existing format picker; if the frame has no player, it opens native page discovery instead. The menu is registered for page and frame contexts, uses the clicked frame for scoped auth, and never replays the control's click or POST.
- Smart Select now proposes an inline page SHA-256 only when one clearly labelled hash is adjacent to a scope containing exactly one reusable file link. The bridge forces checksum-bearing requests through native review. The review shows the full hash and page origin; a default-off checkbox is required before it reaches the engine. The engine verifies it before publication and retains mismatches as Suspect. No checksum sidecar is fetched, and ambiguous or unlabelled hashes are ignored.
- Chrome interception boundary: Chrome MV3 cannot cancel arbitrary download requests for a normal unpacked extension. VESPER accepts only a newly observed, still-unstarted Chrome download for which Chrome reports zero received bytes; a completed or already-progressing Chrome download remains Chrome-owned. Even for eligible requests the helper checks response identity before Chrome is paused, and the native transfer must be accepted before VESPER lists it. ## Compatibility and operational limits

No runtime dependency, language, alternate UI framework or database migration was added to VESPER. Native SQLite and durability/publication contracts remain. Enum output values were appended, not renumbered. New bridge fields are optional; an old extension will not gain the new controls. Use the matching 1.0.2 app/extension for integration.

Secrets are absent from plans, recovery manifests, test fixtures, delivery reports and archives. A private transfer that loses its in-memory context on restart must re-authorize/re-resolve rather than replay credentials to another host. Authenticated merge/DASH contexts unsupported by the existing engine are still rejected rather than silently discarded. Do not use the live example's expiring URL as a fixture.

The workspace preview is only a read-only file explorer over real source and deliverables. It is not part of VESPER, not in its patch, and introduces no Next.js/PostgreSQL dependency into the Windows application.
